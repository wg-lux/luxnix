# Production setup: application secrets with sops-nix

This runbook moves an explicit list of host-export application secrets from
`sync-secrets` to sops-nix on a host with operator-unlocked storage. Follow the
phases in order. Each phase ends with a checkpoint; do not continue past a
failed checkpoint. No host uses this yet.

After the last phase, a reboot works like this, without an administrator,
GitHub or the controller:

1. Local staff enter the storage passphrase once (`Unlock luxnix-secrets:`).
2. The machine installs the secrets, opens application storage from its
   sops-installed key and starts the database and application.
3. The person signs in with their own account password.

## What changes and what does not

| Moves to sops-nix | Stays as it is |
| --- | --- |
| Listed export names from `~/.lxv/deploy/<host>/` | Admin and client account passwords (boot copy) |
| The application volume's automatic unlock key | The `luxnix-secrets` passphrase, which never depends on sops |
| The lx-annotate application master key (optional) | The key value itself: it must stay the one that encrypts existing data |
| | Secrets generated by `managed-secrets` and secrets fetched from Vault |
| | Recovery passphrases and their custody |

The migrated secrets remain protected while `luxnix-secrets` is locked: only a
per-host age key on that volume and the operator's key can decrypt them. This
does not protect unrelated files on an unencrypted root filesystem.

## Roles

| Role | Does |
| --- | --- |
| Secrets custodian | Owns the private repository, the operator age key and the host files |
| Operator | Runs inventory, build and deployment steps from the reviewed checkout |
| Local staff | Enter the storage passphrase at the host |

## Phase 0: one-time fleet setup (secrets custodian)

Run controller commands inside `devenv shell`, which provides `sops` and `age`.

1. **Create a private repository** that only custodians can write, for example
   `wg-lux/luxnix-secrets`. Never put it into `flake.nix`: a flake input is
   fetched for every host and breaks evaluation for anyone without access.
   Hosts pin it in inventory instead (phase 3) and fetch it only when used.
2. **Create the operator age key** on the controller's encrypted storage:

   ```bash
   install -d -m 0700 ~/.config/sops/age
   age-keygen -o ~/.config/sops/age/keys.txt
   ```

   Keep an encrypted copy in recovery custody. With this key the custodian can
   re-encrypt any host file, so a lost host key never loses data.
3. **Lay out the repository:**

   ```text
   .sops.yaml
   hosts/<host>.yaml        one encrypted file per host
   ```

   ```yaml
   # .sops.yaml
   keys:
     - &operator age1<operator-recipient>
   creation_rules: []       # one rule per host, added in phase 1
   ```

Checkpoint: the repository exists, is private, and the operator key works
(`age-keygen -y ~/.config/sops/age/keys.txt` prints a recipient).

## Phase 1: host identity (operator, then custodian)

1. In `ansible/inventory/host_vars/<host>.yml`, enable the mode without any
   secrets yet. This removes SSH-key decryption on the host and installs
   `luxnix-sops-storage`:

   ```yaml
   host_nixos:
     security.sops.operatorStorageKey.enable: true
   ```

2. Generate, build and deploy with the documented workflow:

   ```bash
   devenv tasks run autoconf:check
   devenv tasks run autoconf:generate
   nix build '.#nixosConfigurations.<host>.config.system.build.toplevel' --no-link
   devenv shell check-connectivity <host>
   # on the host, from the reviewed checkout (rebuild-host-switch):
   sudo nixos-rebuild switch --flake '/home/admin/luxnix#<host>'
   ```

3. On the host, with storage unlocked:

   ```bash
   sudo luxnix-sops-storage init
   ```

   It refuses an unmounted or unencrypted volume, never overwrites existing
   keys, and prints two public values: the host's **age recipient** and its
   **read-only deploy key**.
4. Custodian: add the deploy key to the private repository as a **read-only**
   deploy key. Add the recipient and a creation rule to `.sops.yaml`:

   ```yaml
   keys:
     - &operator age1<operator-recipient>
     - &gc-10 age1<host-recipient>
   creation_rules:
     - path_regex: ^hosts/gc-10\.yaml$
       key_groups:
         - age: [*operator, *gc-10]
   ```

   Never add SSH-derived recipients.

Checkpoint: `sudo luxnix-sops-storage status` reports the age key present.

## Phase 2: host secrets file (secrets custodian)

Work in a private terminal with `TMPDIR` on tmpfs, so sops's editor copy never
reaches disk:

```bash
export TMPDIR="$XDG_RUNTIME_DIR"
sops edit hosts/<host>.yaml
```

1. **Volume key.** Add `volume-key-luxnix-app-storage` with a fresh random
   value from `openssl rand -hex 32`. It becomes an additional LUKS key in
   phase 4; the recovery passphrase stays.
2. **Application secrets.** List the candidates by name only:
   `ls ~/.lxv/deploy/<host>/`. Move each selected name with its export file
   name as the sops key. Prefer issuing a fresh value where the consumer allows
   it. Never move:
   - account passwords (`SCRT_local_password_admin_password*`,
     `SCRT_client_user_password*`); evaluation rejects them;
   - anything needed before storage unlock or for the recovery connection;
   - secrets that `managed-secrets` generates or Vault delivers, except the
     lx-annotate master key through its dedicated option in step 3.
3. **lx-annotate master key (optional).** lx-annotate decrypts its storage
   backend with the key named by `LX_ANNOTATE_MASTER_KEY_FILE`. To deliver it
   from sops, add `lx_annotate_master_key` with the host's **existing** key,
   never a fresh one: a new key cannot decrypt existing data. Copy it without
   printing it or putting it on a command line; `sops set` expects a JSON
   string, which `jq -Rs .` produces:

   ```bash
   # managed-secrets hosts (the default): the key generated on the host
   ssh admin@<host> sudo jq -Rs . /etc/secrets/vault/lx_annotate_master_key \
     | sops set --value-stdin hosts/<host>.yaml '["lx_annotate_master_key"]'
   # Vault-delivered hosts: the app_master_key field of the host's payload
   vault kv get -field=app_master_key <host-payload-path> \
     | jq -Rs . | sops set --value-stdin hosts/<host>.yaml '["lx_annotate_master_key"]'
   ```

4. Commit, push, and record the commit hash.

Checkpoint: `sops decrypt hosts/<host>.yaml >/dev/null` succeeds with the
operator key, and the file lists only the intended keys
(`sops decrypt --extract '["volume-key-luxnix-app-storage"]' hosts/<host>.yaml >/dev/null`
succeeds; never print values).

## Phase 3: stage (operator)

1. Pin the repository and list the secrets in the host's inventory. Keep the
   volume key `staged`, so the volume still prompts while the key is installed:

   ```yaml
   host_nixos:
     security.sops.operatorStorageKey.enable: true
     security.sops.operatorStorageKey.secretsRepository.url: '"ssh://git@github.com/wg-lux/luxnix-secrets.git"'
     security.sops.operatorStorageKey.secretsRepository.rev: '"<commit-from-phase-2>"'
     security.sops.operatorStorageKey.volumeKeys.luxnix-app-storage: '"staged"'
     security.sops.operatorStorageKey.applicationSecrets.<EXPORT_NAME>.restartUnits: '[ "<unit>.service" ]'
     security.sops.operatorStorageKey.consumers: '[ "<service-reading-the-secret>" ]'
   ```

   If the host file holds `lx_annotate_master_key`, also add:

   ```yaml
   host_services:
     luxnix.lxAnnotateLocal.runtime.sopsMasterKey.enable: "true"
   ```

   lx-annotate then reads `LX_ANNOTATE_MASTER_KEY_FILE=/run/secrets/lx_annotate_master_key`,
   a file on sops-nix's ramfs owned by the service user (mode `0400`). The
   application gets the path, never the key value in its environment; the
   master-key gate still rejects an inline `LX_ANNOTATE_MASTER_KEY`. Every
   lx-annotate unit orders after `sops-install-secrets.service`, and
   managed-secrets stops generating the key. Evaluation fails if Vault or
   clustered master-key delivery is also enabled.

   The repository is fetched only for hosts with secrets or volume keys.
   Public CI and other hosts never need access.
2. Generate, build on the controller (custodian access), connectivity check,
   then `rebuild-host-switch` on the host as in phase 1. The host fetches the
   pinned commit with its deploy key.
3. From now on `sync-secrets` skips the listed names for this host.

Checkpoint: `sudo luxnix-sops-storage status` shows `ok` for the age key,
`sops-install-secrets.service`, every listed path and the installed volume
key. It shows `FAIL … enrolled` for the volume key; that is expected here.
With the lx-annotate master key, also
`sudo cmp /etc/secrets/vault/lx_annotate_master_key /run/secrets/lx_annotate_master_key`
prints nothing and `systemctl is-active lx-annotate-master-key-check.service`
is `active` (it runs `verify_encrypted_storage` against existing data).

## Phase 4: enroll the volume key (operator, at the host)

```bash
sudo luxnix-sops-storage enroll luxnix-app-storage
```

Enter an existing passphrase of `luxnix-app-storage` when asked. The command
adds the installed key as an additional LUKS key, keeps every existing
keyslot and verifies the new key.

Checkpoint: status shows `luxnix-app-storage: volume key enrolled (staged)`, and
the recovery passphrase still opens the container:
`sudo cryptsetup open --test-passphrase <container>`.

## Phase 5: activate (operator)

Set the volume key to `active`, then generate, build and switch as before:

```yaml
    security.sops.operatorStorageKey.volumeKeys.luxnix-app-storage: '"active"'
```

Checkpoint: every status line is `ok`, including `luxnix-app-storage: open`.

## Phase 6: cold-boot acceptance (operator and local staff)

With an authorized reboot window and someone at the host:

1. Reboot. Exactly one prompt appears: `Unlock luxnix-secrets:`.
2. The login screen appears; the person signs in with their own password.
3. Without further input: `sudo luxnix-sops-storage status` is all `ok`,
   `systemctl --failed` is empty and `systemctl is-active lx-annotate.service`
   is `active`.
4. Record the result in the deployment record. Roll out to the next host only
   after this passes.

## Phase 7: clean up (secrets custodian)

- Rotate every migrated credential that was ever encrypted to an SSH host key
  in public history, and remove SSH recipients from affected files.
- Keep the old export files only until acceptance; `sync-secrets` no longer
  deploys them to this host.
- Keep `/etc/secrets/vault/lx_annotate_master_key` on the host as long as a
  rollback is possible. Without it, disabling `sopsMasterKey` lets
  managed-secrets generate a new key that cannot decrypt existing data.

## Rollback

| From | Action |
| --- | --- |
| Phase 5 | Set the volume key back to `"staged"` and switch: the volume prompts again. |
| Phase 3 | Remove the `applicationSecrets` entries and `volumeKeys`, switch, then `devenv shell sync-secrets --limit <host>` restores the old files. |
| lx-annotate master key | Confirm `/etc/secrets/vault/lx_annotate_master_key` is still present, set `sopsMasterKey.enable` back to `"false"` and switch. |
| Phase 1 | Set `security.sops.operatorStorageKey.enable: false` and switch. |

## Failures

| Symptom | Cause and action |
| --- | --- |
| Application storage stays locked after boot, journal names `luxnix-operator-storage open` | Automatic key missing or rejected. Open it with the recovery passphrase: `sudo luxnix-operator-storage open luxnix-app-storage`, then check `luxnix-sops-storage status`. |
| `sops-install-secrets.service` failed | `journalctl -u sops-install-secrets.service -b`. A missing age key or a host file not encrypted to the host's recipient are the usual causes. |
| `lx-annotate-master-key-check.service` failed after enabling `sopsMasterKey` | The sops value is not the key that encrypts existing data, or it is missing. `journalctl -u lx-annotate-master-key-check.service -b`; correct `lx_annotate_master_key` in the host file. Never enable auto-generation as a fix. |
| Build fails: `Failed to fetch git repository` | The deploy key is not registered, or the pinned commit does not exist. |
| Age key lost (volume replaced) | Run `luxnix-sops-storage init` again, update the recipient in `.sops.yaml`, re-encrypt with `sops updatekeys hosts/<host>.yaml`, pin the new commit. |

The startup ordering, safeguards and option reference are in
[Manually unlocked site storage](operator-unlocked-storage.md#application-secrets-with-sops-nix).
