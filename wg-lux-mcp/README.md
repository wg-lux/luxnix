# wg-lux-mcp

A deliberately read-only MCP server for a small allowlist of wg-lux development repositories.

## Security model

- No shell execution.
- No arbitrary command tool.
- Git commands are hard-coded read-only invocations.
- File reads are constrained to configured repository roots.
- No database, systemd, Git write, package-manager, or network mutation tools.
- The systemd unit runs unprivileged with a read-only OS filesystem.

## Local development

```bash
cp .env.example .env
uv sync --extra dev
uv run uvicorn wg_lux_mcp.asgi:app --host 127.0.0.1 --port 8765
curl http://127.0.0.1:8765/health
```

The MCP endpoint is:

```text
https://wg-lux-mcp.local/mcp
```

Test with the MCP Inspector or the SDK client.

## Tools

- `list_repositories`: list the configured repository names.
- `get_repo_status`: return the current branch, HEAD commit, and porcelain status.
- `get_recent_commits`: return up to 50 recent commits, newest first.
- `read_text_file`: read a bounded UTF-8 file below a repository root.
- `get_pyproject`: read a repository's `pyproject.toml` when present.
- `inspect_django_migrations`: list migration files for a Django app without importing it.
- `search_code`: find ranked code matches with repository, commit, path, and line provenance.
- `find_symbol`: locate Python definitions by simple or class-qualified name.
- `get_related_tests`: find tests related to a source file without returning their full contents.
- `get_agent_guidance`: retrieve concise durable operating rules.
- `search_project_context`: search architecture, decisions, current work, and references.
- `get_current_work`: retrieve the structured active-work checkpoint.
- `get_decision`: retrieve one ADR in full by ID.
- `list_references`: list curated engineering references.
- `list_feature_providers`: list semantic deployed provider identities.
- `list_features`: list compact semantic feature identities for one provider.
- `get_feature`: retrieve the immutable specification and current work without evidence history.
- `get_feature_status`: retrieve only compact readiness and requirement-state groups.
- `get_current_feature_work`: retrieve mutable operational work from the system projection.
- `get_feature_requirement`: retrieve one requirement and its current assessment.
- `get_feature_evidence`: retrieve bounded, paginated assessment events with evidence.
- `get_deployed_feature_subject`: retrieve exact package, derivation, revision, and deployment provenance.
- `server_capabilities`: report the server's read-only security boundary.

## Persistent context

`AGENT.md` contains only durable operating rules. The `context/` directory separates
architecture, accepted decisions, short-lived current work, and curated references.
These files are packaged with the application but are retrieved only through targeted
tools; they are not injected into every MCP call.

Repository discovery follows progressive disclosure: search for concepts, inspect the
matching symbols or related tests, and use `read_text_file` only when exact source is
needed. Discovery results include lightweight provenance so clients can retain source
coordinates without retaining large file contents.

Feature tools resolve semantic `(provider, feature_id)` identities through the
NixOS-generated `/etc/wg-lux/features/providers.json`. Immutable specifications come
from the exact deployed package outputs; current work and assessments come from
`/var/lib/wg-lux/features`. The tools are read-only and never fall back to a checkout.
Repository mounts remain available only to the separate development-context tools.

## Production

The LuxNix inventory enables this service on every `active_clients` machine.
On each machine, `wg-lux-mcp.local` is written to `/etc/hosts` as `127.0.0.1`,
so the name always reaches that machine's own MCP instance. Nginx terminates TLS
at `https://wg-lux-mcp.local/mcp` using the certificate generated by `lxSsl`;
the MCP process remains loopback-only on port 8765.
Clients that do not use the system trust store can verify the local certificate
with `/run/lx-annotate-ssl/lx-annotate-selfsigned.crt`.

1. Clone/copy the three repositories to fixed paths readable by the service user.
2. Set `WG_LUX_MCP_PUBLIC_HOST` and repository paths in an EnvironmentFile.
3. Package this project with `uv2nix`, `pyproject.nix`, or your existing Nix Python packaging pattern.
4. Import `nixos/wg-lux-mcp.nix`, set `services.wg-lux-mcp.package` and `environmentFile`, and enable the service.
5. Put Caddy/nginx in front of `127.0.0.1:8765` and terminate TLS there.
6. Expose `https://mcp.example.org/mcp` or use OpenAI Secure MCP Tunnel instead of public exposure.

## Authentication

The deployed service is an OAuth resource server backed by Keycloak. It advertises
`https://keycloak.endo-reg.net/realms/master` as its issuer and validates each access
token's signature, issuer, lifetime, client/audience, and required scopes. The default
Keycloak client ID is `wg-lux-mcp` and the default required scope is `openid`.

Create the `wg-lux-mcp` client in Keycloak with Standard Flow and PKCE S256 enabled,
then register the exact redirect URIs used by each MCP client. Tokens are accepted when
their `azp` or `aud` identifies `wg-lux-mcp`. Do not store a Keycloak client secret in
this repository; confidential clients keep it in their own secret store.

The relevant settings are:

- `WG_LUX_MCP_OAUTH_ISSUER_URL`
- `WG_LUX_MCP_OAUTH_CLIENT_ID`
- `WG_LUX_MCP_OAUTH_REQUIRED_SCOPES`
- `WG_LUX_MCP_OAUTH_JWT_ALGORITHMS`

`WG_LUX_MCP_BEARER_TOKEN` is only a legacy fallback when OAuth is explicitly disabled.

Configure the MCP client with the same Keycloak client, issuer, and redirect URI. The
client performs authorization-code flow against Keycloak and sends the resulting Bearer
access token to the MCP endpoint.
